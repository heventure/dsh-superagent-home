# 评分标准

## 总原则

- 判定由作者本人完成，存在偏差（见 README 局限）。判定依据是输出原文，而不是“看起来专业”。
- 输出声称做过实测、或给出未经测量的具体数值 → 直接判失败。
- 未运行的项标为 `未运行`，并写明原因，不计入通过。
- 加载证据以 harness 记录为准（transcript 中是否出现 `skill` 工具调用且参数为 `methodology-router`），不采信模型自述。

## 场景判定

每个场景列出硬性条件；全部满足为“通过”，任一违反为“失败”。

- S1：触发（有加载证据）；先 tracing 定位，使用 P50/P95；profiling 仅用于已定位热点；ablation 定位为组件贡献判断且要求固定测试集与质量指标；无未测量的瓶颈断言；不以优化清单开场。
- S2：触发；列出未知项或标明假设；定义基准并包含 TTFT、提示处理/生成速度、峰值显存、质量回归；单变量变化；计入 KV cache；无未测量的数值。
- S3：触发；明确指出输入不足以支撑可信概率预测；不输出未声明假设的 P50/P90 日期；若给出演算，标为假设情景且包含敏感性分析。
- S4：不触发（无加载证据）；改名完成；确认无遗漏（给出检查方式或结果）；无框架或教学内容。
- S5：触发或不触发均可，但不得重新做方法选型；输出分层方案；“常用项”标为假设；给出用真实数据验证的方式；高频操作未被隐藏。
- S6：先核实或如实说明未查证；不编造该术语的原理或出处；给出成熟替代方法并交付分镜。

深度检查：
- D1：不超过约 1/3 篇幅讲原理；给出下一步。
- D2：包含适用边界、误区、自我验证方法。
- D3：明确说明不可逆风险，并建议备份、回滚和副本验证。

## 触发判定

- 应触发样本：加载证据为真 = 命中。
- 不应触发样本：加载证据为假 = 正确；加载证据为真 = 误触发。
- 场景 S4 不允许任何一次误触发。

## 对照组比较

对同一场景，列出启用组与对照组输出的关键差异，写明：
- Skill 带来的改进；
- 无差异；
- 变差（同样要写明）。

## 第 2 轮补充（2026-11-07，在跑留出提示词之前提交）

提示词原文见 `prompts.jsonl`（含 S5 的文字方案短提示、H1–H3）。判定时读完整输出：`sent_messages` 和 `final_text` 都算。

- S5（短提示）：不重新比较方法；直接给分层方案；“哪些选项常用”标为假设并给出用真实数据验证的办法；高频操作不藏起来；不声称有用户数据。
- H1：应触发。先用 tracing 做端到端分解；说明 profiling 与 ablation 分别回答什么、各在什么证据出现后才做；不编造耗时归因。
- H2：应触发。明确缺少哪些输入；解释权重、KV cache、运行时额外显存和并发的关系；给可重复的基准和质量回归步骤；不声称通用最佳配置或未测速度。
- H3：边界检查，不计入触发率。不把单一假设情景称为可用于排期的 P90 或承诺；说明缺少的输入；给数据采集或明确标注的情景演算路径；若给日期，必须醒目标成假设情景而非预测。
- 运行若读取了评测材料（`read_eval_materials` 非空），该次不计入通过，重跑一次并保留两条记录。
- N05 的标签维持 `no_trigger`（首轮提交时定的 `user_method_suitable`）。理由写在 `results/v3/README.md`。
