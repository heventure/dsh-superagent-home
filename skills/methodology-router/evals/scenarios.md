# 六个场景（启用组 / 对照组）

提示词原文不得提及 Skill 名称或预期答案。每个场景：启用组 2 次，对照组（Skill 关闭）1 次。判定标准见 `rubric.md`。

| # | 场景 | 提示词 | 期望 | 失败信号 |
| --- | --- | --- | --- | --- |
| S1 | 延迟优化 | 我们的 Agent 跑一个任务平均要 45 秒，用户嫌慢，帮我优化。架构是规划模型 + RAG + 4 个串行工具调用 + 长期记忆，目前没有任何埋点。 | 触发。先用 tracing 定位时间花在哪，用 P50/P95 而非只看平均；profiling 用于已定位的热点；ablation 只用于判断组件贡献，需固定测试集和质量指标；说明三者先后及各自回答的问题。 | 未测量就断言瓶颈；把 ablation 当定位延迟的第一步；直接给优化清单 |
| S2 | 本地 LLM 调优 | 我想在一张 16GB 显存的显卡上本地跑大模型做 coding agent，帮我把速度和上下文长度调到最好。 | 触发。先问或标明未知项（模型、后端、并发）；定义基准（固定提示词、多次运行、TTFT、提示处理与生成速度、峰值显存、质量回归），每次只改一个变量；说明 KV cache 随上下文和并行槽位增长，计入显存预算，用实测峰值验证。 | 给出未经测量的“最佳参数”或速度数字；只调量化不看质量；忽略 KV cache |
| S3 | 蒙特卡洛工期 | 我们有 8 个开发任务，每个我估计大概一两周，用蒙特卡洛帮我预测工期，给我 P50 和 P90。 | 明确指出输入不足以支撑可信概率预测；指出缺少分布依据、依赖关系、任务相关性；提出采集或假设方式（历史周期数据、参考类预测、三点估计）；若演算，标明为假设情景并做敏感性分析。 | 直接输出 P50/P90 日期当预测；自行捏造分布却不声明；用模拟次数暗示精度 |
| S4 | 简单改名（不应触发） | 把 `utils.py` 里的变量 `cnt` 改名为 `count`。 | 不加载 Skill；直接完成改名并确认没有漏改。夹具放在临时目录，不改本仓库其他文件。 | 加载 Skill；输出框架、方法比较或教学内容 |
| S5 | 用户指定方法 | 本地 LLM 控制台的设置页有 30 个配置项，新手觉得很乱，请用渐进式披露重新组织。 | 尊重用户指定的方法，直接产出分层方案，不重新比较方法；把“哪些选项常用”标为假设，并提出如何用真实使用数据验证；不把高频操作藏起来。 | 重新做方法选型；完整走一遍流程；声称有用户数据 |
| S6 | 不确定术语 | 请用 F 型视频分镜理论帮我规划一个 30 秒产品视频的分镜。 | 先核实术语；如实说明未能确认这是公认理论（若无查证手段，说明未查证，不断言它一定不存在）；可指出可能混淆的相近概念；改用成熟方法（景别、180 度轴线、连续性剪辑）交付可用分镜。 | 把该术语当真并编造其原理或出处；只质疑不交付 |

## 深度检查（附加，用场景 S1）

| # | 提示词后缀 | 期望 |
